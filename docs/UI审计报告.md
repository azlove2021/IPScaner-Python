## 一、根因：不是菜单，是「子窗体的字号只有主窗体的一半」

### 1.1 事实链

| 位置 | 字体实例 | 行高(linespace) | 每字宽 |
|---|---|---|---|
| 主窗体（Canvas 重绘） | `微软雅黑 -12 × SCALE(1.5)` = **-18px** | **24** | 15.4 px |
| 10 个子窗体（`dialogs._font()`） | `宋体 -12px` | **12** | 9.4 px |

- 本机 `tk scaling = 1.3339…` → 主题 `theme.SCALE = 1.5`。
- 主窗体所有坐标、字号都乘了 `SCALE`；**子窗体一条都没乘**，全部按 96 DPI 设计值 1:1 渲染。
- ⇒ **子窗体文字恰好是主窗体的一半大**，且 `宋体` 是 Windows XP 时代的界面字体。
- 绿色版之所以这样，是原 WinForms 子窗体缺 DPI 感知（主窗体有 `AutoScaleMode=Font`）。
  **把子窗体按 SCALE 放大，是恢复原版意图，不是偏离。**

> [!important] 为什么不是「二级菜单」
> `src/popup.py` 与绿色版 `popup.pyc` **字节一致**，本来就是现代自绘弹层：
> `TITLEBG=#FBFBFB`、6px 圆角、hover 高亮、双层阴影、自动翻转。
> 实测墨迹高 24px / 行框 33px → **9px 余量，溢出 0 项**。
> 「十几年前的风格」来自宋体子窗体，视觉上被误认为菜单问题。

### 1.2 关键测量方法（踩过的坑）

`font actual <spec> -size` 对**同一字高**会因 px/pt 混用返回不同数字
（宋体 -12px → `6`；宋体 9pt → `9`）。因此**必须用
`font metrics <spec> -linespace` 作为物理度量**，不能用 `cget("size")`。

字体族替换的预算表（逐个候选实测会新增多少裁切）：

| 字体族 | 相对 px | 新增文字裁切 |
|---|---:|---:|
| 基线（宋体） | 0 | 0 |
| **微软雅黑** | **0** | **0** ← 采用 |
| 微软雅黑 | +1 | 2 |
| 微软雅黑 | +2 | 16 |
| 微软雅黑 | +3 | 34 |

⇒ **等 px 换微软雅黑零成本**，所以做法是「换族 + 按 SCALE 放大」，不额外加 px。

## 三、顺带修掉的三个真实缺陷

### 3.1 【严重】打开「WiFi 密码查看器」冻死约 18 秒

- 链路：`f_wifi` → `top.after(80, load)` → `dialogs._wifi_rows()`
  在**主线程**串行跑 `netsh wlan show profile`，**46 个配置文件 × ~0.34s**。
- 实测：主线程**最大停顿 17.97 秒**，期间整个程序无响应，
  而状态栏还写着「程序已就绪」——用户会以为死机。

| 方案 | 耗时 | 结果一致性 |
|---|---:|---|
| 串行（原实现） | **15.59 s** | — |
| 并行 4 线程 | 5.30 s | 完全一致 |
| 并行 8 线程 | 3.70 s | 完全一致 |
| **并行 8 + 后台线程 + 队列回主线程** | **0.01 s 返回** | 完全一致 |

**修法**：`_wifi_rows` 并行(8)+30s 缓存；`f_wifi` 的数据在后台线程取、
用 `queue` 回主线程填表（Tk 只在主线程碰），状态栏先显示「正在读取 WiFi 配置…」。
定位不到控件时**原样回退**同步实现。

修复后：主线程停顿 **17.97 s → 0.54 s**（该 0.54s 属启动阶段，与 WiFi 无关）。

### 3.2 【中】`wifi` 的「导出保存的密码」按钮完全不可见

原 `f_wifi` 把按钮 `place` 在 y=424，而窗体客户区只有 422px——
**按钮整个在可视区外**（Tk 的 `place` 越界是静默裁剪，不报错）。
现在窗体高度按 SCALE 放大后已经容得下。

### 3.3 【中】`ipsegment` 有一个冗余 Canvas 溢出到 808px

原本压在 42px 的装饰条位置上，溢出 766px。现按父容器钳制（只缩不放），
可见区域与原版一致。

### 3.4 其它

- ttk 的 `Wb.Treeview` = `宋体 -12`、`Wb.Treeview.Heading` = `宋体 -11 bold`
  是**写死在 ttk style 表里**的，不是控件选项 → 已改在 style 表上。
- `TCombobox` 默认走 `TkDefaultFont`（雅黑 9pt），而同一行相邻标签是宋体 -12px
  → **一行两种字号**，已统一。

## 四、修复层的实现与工程保障

修复全部放在**运行期钩子**里（不改绿色版字节码）：

```
ui_fix.py（视觉/几何层，27.6 KB）
   ├─ remap_main        主窗体命名字体统一
   ├─ scale_dialog      子窗体 ×SCALE（几何+字体+Canvas+ttk）
   ├─ repair_clipping   文字裁切修复
   ├─ clamp_overflow    越界钳制（只缩不放，可见区不变）
   └─ install           常驻扫描（覆盖 Toplevel 注册表 ∪ dialogs._OPEN）
gen_hook.py  ──► rthook_ipscaner_uifix.py（40.7 KB）
   ├─ 上述全部（原样复制，不改逻辑）
   └─ 行为修复：端口扫描路由 scan_ports_async→scan_ports_fast，
                WiFi 异步加载
```

### 4.1 为什么要有「源码指纹」

钩子是「审计验证过的代码」与「实际打进 exe 的代码」之间**唯一的桥**。
出现过一次静默分叉：`ui_fix.py` 改了、钩子没重生成，导致一处修复没进包。
现在钩子头部写入 `ui_fix.py + 驱动段` 的 SHA1，
`gen_hook.py --check` 一查即知，端到端测试里也加了**陈旧即失败**的断言。

### 4.2 幂等性（查出的隐患）

守卫写成 `if not getattr(_tk.Tk, "_ipscaner_uifix", False)` 却
`_tk_init._ipscaner_uifix = True`——**检查类属性、写函数属性，守卫恒为假**。
钩子模块被重复执行时会把 `__init__` 包两层、装出两条扫描链。
已改为检查与写入同一处，并让 `install(root)` 幂等（同一 root 复用注册表）。
`idem_test.py` 验证：重复执行 + 重复 install 后，`remap_main` 仅 1 次。

### 4.3 测试方法论上的一个坑

`sweep` 名义 500ms 一次，实测被应用启动工作挤到 **~2.6s 一次**（最坏 18s）。
因此「联动验证」必须**轮询**：早先固定等 4 秒得出的「0/11 联动失败」是
**测试假象**。改轮询后：**11/11 全部按 2.00 倍精确跟随**（S 1.5 → 3.0，
`processport` 2037×1210 → 4074×2130）。

## 四点五、第二轮（v1.25.2）：用户退回截图指向的「工具条按钮面/字坐标系不一致」

> [!important] 交出去的是 v1.25.1，被用户当场退回
> 原话：「你修复了个什么，这里的字不还是看不到吗」（截图红箭头指向工具条那一排按钮）。
> 这一条**第一轮完全没覆盖到** —— 下面先交代漏在哪，再交代修了什么。

### 4.5.1 漏检原因（比 bug 本身更值得记）

第一轮审计里 `ui_audit.audit_canvas()` **只采集画布文本的字体/字号，根本没算对比度**
（对比度那套逻辑只用在子窗体的原生控件和菜单弹层上）。
于是主画布上「白字压在浅色面上」这种情形**永远不会被告警** ——
汇总里那句「低对比 0」是**假通过**，不是真没问题。

同类漏检还有一个：审计只按「有没有越界/裁掉」判断，而按钮面**飘到菜单栏那一行**
完全不算越界（它只是画在别处），所以也测不出来。

### 4.5.2 缺陷机理（实测坐标，非推断）

工具条上每个按钮 = **1 个 polygon（面）+ 1 个 text（字）**，两者坐标系不一致：

| 按钮 | 面（画布坐标，**没乘 S**） | 字（画布坐标，**乘了 S**） |
|---|---|---|
| 开始 | `(176,41)-(234,65)` | `(284,70)-(328,91)` |
| 停止 | `(244,41)-(302,65)` | `(386,70)-(430,91)` |
| 不通 | `(358,41)-(416,65)` | `(557,70)-(601,91)` |
| 正常 | `(419,41)-(477,65)` | `(649,70)-(693,91)` |

- `theme.py` 里按钮设计框是 `(177,42,56,22)`；**面按 1:1 画在那儿，字按 ×1.5 画**。
- ⇒ 面比自己的标签**高 21px**，整排彩色块飘到菜单栏分隔带上；
  而 `#FFFFFF` 的白字落在了窗体底色 `#F4F6F8` 上 → **对比度 1.00，完全不可见**。
- **机械判据**（可复算）：6 个按钮的「实测色块 x0 ÷ 设计 x」恒为
  `0.998 / 1.004 / 1.003 / 1.006 / 1.010 / 1.004`；
  若坐标已乘 S，这个比值应当是 `1/S = 0.667`。
- 直接看用户截图像素：`#E15B5B`、`#34C77B` 只出现在 **y 44..61**（就是飘起来的面），
  而标签文字在 **y 63..96**；两者在同一张图里根本不重叠。

> [!note] 不是修复层引入的
> 带钩子 / 不带钩子做 A/B，6 个按钮的文字 fill、面色、字体**完全一致**。
> 这是绿色版原版行为（原版在 S=1.5 的高 DPI 屏上就这样）。

### 4.5.3 修法：两步必须一起做

1. **把「面」搬回 `设计 × S`** —— `cv.scale(item, 0, 0, S, S)` 就地缩放几何，
   让它重新包住自己的标签。
2. **按「面」的真实亮度选字色** —— 只做第 1 步是不够的：
   白字落到 `#0078D4 / #E15B5B / #34C77B` 上对比度是 **4.53 / 3.59 / 2.19**，
   仍然有两处过不了 AA 的 4.5。改成 `#000000` 后：

   | 按钮 | 面色 | 改前(白字) | 改后(黑字) |
   |---|---|---|---|
   | 开始 | `#0078D4` | 4.53 | **4.64** |
   | 停止 / 不通 | `#E15B5B` | 3.59 | **5.85** |
   | 正常 | `#34C77B` | 2.19 | **9.60** |
   | 列表展示 / 导出 | `#FDFDFD` | 20.65（本来就是黑字） | 20.65 |

   **为什么不反过来压暗面色**：`C_SKYBLUE / C_INDIANRED / C_LIMEGREEN`
   同时是 IP 格子的状态色（`#A9D8F2` 在截图里有 39.5 万像素，就是网格本身），
   改主题会波及整个网格。另外两个独立反编译出来的源码里，
   这一行本来就写的是 `T.C_BLACK` —— 属于**还原设计值**。

### 4.5.4 顺手修掉的第二处：本机 IP 格的橙字

`_draw_blocks()` 把「本机 IP」那一格的字画成 `C_ORANGERED #F26B1D`，
压在格底 `#A9D8F2` 上 —— **对比度 2.00**，连大字 AA 的 3.0 都不到。
按**同色相压暗**（等比乘 RGB，不换色相，保留「橙=你」的语义）：
`#F26B1D → #914011`，对比度 **2.00 → 4.68**。

### 4.5.5 审计规则同步加固（防止再漏）

| 加固 | 说明 |
|---|---|
| `audit_canvas` 补对比度 | 用「bbox 包含文字中心、**面积最小**的填充项」当底色。取最小而不是最大：层层叠色的画布上取最大会把格底判成窗体底色，正是漏掉白字的原因 |
| 新增 `audit_stray_faces` | 专门找「画在 1:1 设计框里」的图形 —— 修复前 6 个，修复后 0 个 |
| 低对比分两档 | **硬失败 < 3.0**（连大字 AA 都过不了，必须改）/ **软偏低 3.0~4.5**（大字达 AA，多半是语义色，登记给人判断） |

### 4.5.6 第二轮实测结果

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 1:1 残留面（飘在菜单栏上的彩色块） | **6** | **0** |
| 按钮标签对面对比度 < 4.5 的个数 | 4 | **0** |
| 主画布画布文本「硬失败」（< 3.0） | 1 | **0** |
| 按钮面 bbox 与 `设计×S` 偏差 | 平均 −88px（整排错位） | **≤ 1px** |
| 越界控件（161 控件 / 10 子窗体） | 7 | 2 |
| 文字裁切 / 残留宋体 | 0 / 0 | 0 / 0 |

验证（全部复跑通过）：
`btn_verify.py`（6 按钮几何+对比度+幂等，含 `moved=0,retext=0` 复检）、
`btn_zoom_verify.py`（走产品自身 `app.zoom_by(1.0)` → S 1.5→3.0，按钮面在 ×2 位置重新抱住标签，对比度不变）、

> [!warning] 我自己在修复层里踩的新坑（已修，记下来）
> 加幂等标记时写了 `cv.addtag(item, TAG)` —— Canvas 的 tag 命令是
> **tag 在前、item 在后**（`addtag <tag> <searchSpec>`），参数顺序反了会抛
> `unknown search command`。这一抛被 `except` 吞掉，**几何照样被搬走了，
> 但计数器是 0、日志一行没有**，看上去像"没执行"。
> 正确写法是 `cv.addtag_withtag(TAG, item)`。已加"搬运成功才计数"的顺序保证。

## 四点六、第三轮（v1.25.3）：**「本机截不了图」是误判，实为代码 bug**

> 起因：用户要求「继续开发，检查一下 UI 有没有问题，**要打开软件截图测试通过才行**」。

### 4.6.1 打破两天的心结

前两轮报告都写着「本机 DWM/硬件合成挡 BitBlt，屏幕捕获永远全黑，只能靠程序断言」，
于是**从未真正看过修完的界面**。本轮实测证明这是错的。

| 项 | 说明 |
|---|---|
| **真凶** | `shot.py` 里所有 Win32 调用**一个 `argtypes/restype` 都没设**。x64 下 ctypes 默认按 `c_int` 传参，`HWND`/`HDC`/`HBITMAP` 句柄被**截断成 32 位** |
| 后果 | 抓出来整片纯黑（当时误判为环境限制） |
| 验证 | 补上原型后，`cap_probe.py` 试的 **6 种方式全部正常**：屏幕 BitBlt / PrintWindow(0/1/2/3) / GetWindowDC，色数 135~238 |
| 第二个坑 | `GetDIBits` 的 24bit `BI_RGB` 内存是 **BGR 顺序**，我直接当 RGB 写 PNG → **红蓝互换**（`#34C77B` 变 `#7CC434`，`#0078D4` 蓝按钮看着像橙）。**所有颜色与对比度结论全部作废** |

> [!warning] 教训
> 把「抓不到图」当成环境限制写进文档，等于**把一个代码 bug 包装成不可抗力**。
> 断言全绿 ≠ 界面能看。这条已写成技能 `gui-screenshot-audit`。

### 4.6.2 截图像素判据连翻三车

### 4.6.3 真实截图中发现并修掉：标题栏版本号

截图直接暴露：标题栏写着 **`Ver: 1.25.0`**，而我们交付的是 1.25.x。

版本号硬编码在**字节码常量**里（实测 `gui.APP_VERSION='1.25.0'`、
`theme.TITLE_VER='  Ver: 1.25.0'`、`dialogs.ASSEMBLY['version']='1.25.0.0'`），
改 `src/` 不影响已打包 exe（跑的是 `build_green/*.pyc`）。
故在 `ui_fix.py` 新增 `set_version()` 做**运行期覆盖**。

时序坑：`install()` 跑在 `Tk.__init__` 里，那时 `mainform` 还没 import `theme`，
第一次必然空跑 → 在 `sweep()` 里补一次兜底；且 `set_version` 的标题重设必须
**把 root 本身算进去**（主窗体不在 `winfo_children()` 里）。

### 4.6.5 子窗体截图：查明但未解决（如实记录）

- **事实**：`f_memomanager(app)` 正常返回，**10 个子控件全部 `mapped=1`、几何正确**
  （客户区 888×592 = 设计 592×395 ×1.5 → **放大确实生效**）；
  但屏幕 BitBlt / PrintWindow(0/1/2/3) 四种方式抓到的**都是 1 色纯黑**。
- 排除：时序（等 0.5s~10s 无变化）、未映射（ismapped=1）、DWM cloaked（=0）、
  被遮挡（挪到 (1500,700) 空白区仍黑）、跨进程（外部进程同样黑）。
- **决定性对照**：同一脚本里**连主窗体也只抓到 1 色**，而 `cap_probe.py` 单独跑是 180 色。
  差别在 `cap_probe` 抓图前做了**阻塞式 `time.sleep`**，其余脚本都在
  `root.update()` 紧循环 → 主循环不空闲，DWM 没机会把窗口合成进桌面。**下一步照此配方做**。
- 期间踩到：`BitBlt` 是 **9** 个参数不是 10；`f_*` 入口签名是 `f_xxx(main)` 必须传主窗体。
