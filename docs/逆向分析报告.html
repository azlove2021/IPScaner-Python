2架构分析

2.1 分层

gui.main()                         入口：DPI 感知、命令行参数、Config.load、起主循环
  └─ mainform.MainForm            主窗体 = 一块 tk.Canvas，全部控件手绘
       ├─ theme                   常量表（坐标/颜色/字体，全部标注 [SRC]/[MEAS] 来源）
       ├─ menu_def                菜单结构（纯数据，逐项照抄原版 C#）
       ├─ popup.MenuPopup         弹出层 = 独立 Toplevel（overrideredirect + 自绘 Canvas）
       ├─ dialogs.f_xxx           10 个子窗体 = 原生 tk 控件 + 绝对坐标 place()
       └─ core                    系统交互（命令行/socket/网卡/WiFi/CSV），不碰 GUI

分层是干净的：core 零 GUI 依赖（纯 subprocess/socket/csv/ipaddress）， UI 层单向依赖 core。menu_def/popup 是纯数据+纯逻辑， 这也是为什么它们在两代构建之间逐字节一致 —— 没人再动它们。

2.2 渲染架构：为什么主界面用 Canvas 手绘

mainform 分 base/fx 两层：base 只建一次（静态外观 + 254 个色块）， fx 按需重建（悬停高亮、下拉菜单、右键菜单、输入光标）。 ScaledCanvas 把所有坐标乘以 theme.SCALE， 以此复现 WinForms 的 AutoScaleMode=Font 行为 —— 这是它在高 DPI 上能保持观感一致的关键。字体上用负数字号表示像素高度绕开 DPI 缩放， 并为 GDI「ASCII 13px / CJK 14px」的分档差异写了 _f10_for() 按内容挑字号。

2.3 弹出层架构（正确的设计决策）

popup.py 的模块 docstring 明确记录了为什么要离开主 Canvas： Canvas 有裁剪边界，而 WinForms 的 ToolStripDropDown 本来就是独立 WS_POPUP 窗口。旧的 Canvas 方案下「windows命令」23 项、高 445px， 底边 y=469 正好撞上 y=470 起的状态栏 —— 这正是你上一轮修的那个「菜单点了看不到文字」。 现在用 Toplevel + overrideredirect + -transparentcolor， 配上下/左右翻转避让。真机截图确认这个弹层现在是独立窗口且渲染正常。

2.4 并发模型

scan_ports_async 是一个混合分派器：

ports = sorted(set(ports))            # try/except (TypeError, ValueError)
low  = [p for p in ports if p <= low_threshold]   # 默认 1024
high = [p for p in ports if p >  low_threshold]
if low:  _scan_ports_thread(...)      # 200 工线程池（可靠，不漏 135/445）
if high:
    if len(high) >= 512:
        try:    _scan_ports_async(...)         # asyncio Proactor (IOCP)
        except Exception: _scan_ports_thread(...)   # ← 兜底
    else:   _scan_ports_thread(...)

作者在 docstring 里写明了为什么混合：纯 asyncio 高并发回环洪泛会确定性丢掉 135/445， 所以低端口走线程池。这个设计本身是对的。

3Bug 清单（按严重度）

P0绿色版源码丢失

最新构建（含 25 个新函数、现代主题、Ctrl 滚轮缩放、配置持久化）的 .py 已不在磁盘上 —— 全盘检索 def set_static_ip / def scan_ports_async 等 0 命中， 两个 zip 里也只有旧 src。绿色版 exe 内的 pyc 是这段代码的唯一载体。 不找回源码，"完善这个工具"无从下手。

P1asyncio 被排除 + 裸 import → 静默性能回退（不崩溃）

build.py 的 EXCLUDES 里有 asyncio， 绿色版里确实三重确认缺失（PYZ / base_library.zip / _internal 均无）。 而 core._scan_ports_async 的第 3 条指令就是裸的 IMPORT_NAME asyncio，函数体内无 SETUP_FINALLY。

但调用处（scan_ports_async 偏移 218–240）用 try/except Exception 包住了它 → ModuleNotFoundError 被吞掉， 静默回退到线程池。我用劫持 __import__ 的方式在隔离环境实测： 不抛异常、返回结果正确，只是变慢。

按作者自己的 docstring：全端口 1-65535 用 asyncio 约 22s， 纯线程池约 29s —— shipped 版每扫一次全端口就白白慢约 24%，且用户毫无感知。

_scan_ports_async 第 0-6 条指令：
      0  LOAD_CONST        0
      2  LOAD_CONST        None
      4  IMPORT_NAME       asyncio   ← 裸 import
      6  STORE_DEREF       asyncio
P1最优实现 scan_ports_fast 与 scan_ports 是死代码

全 exe 交叉引用核查：

scan_ports_async   ← dialogs.f_portscan.scan_ports_.fn / scan_batch_.fn   （被用 ✓）
scan_ports_many    ← dialogs.f_portscan.scan_seg_.fn                        （被用 ✓）
scan               ← mainform.MainForm.start_scan.work                      （被用 ✓）
probe_hosts_concurrent ← dialogs.f_ipsegment.start_scan.work                （被用 ✓）
scan_ports         ← （无调用者，仅定义）                                    ★ 死代码
scan_ports_fast    ← （无调用者，仅定义）                                    ★ 死代码

讽刺的是：scan_ports_fast 用的是 非阻塞 socket + select，根本不需要 asyncio，docstring 自称 "单 IP 全端口从 ~29s 降到 ~2-3s"。也就是说 —— 最快、且不受 asyncio 排除影响的实现已经写好了，却没接上。 把它接到「单IP全端口」入口上，同时删掉 asyncio 路径， 就能同时修掉 P1 的性能回退和 EXCLUDES 的矛盾。

P1「WiFi密码查看器」导出按钮完全不可见

窗体客户区 545×422，但按钮放在 btn(top, 8, 424, 96, 21, "导出保存的密码", export) —— y=424 > 422，整个按钮落在客户区外。真机截图证实： 底部只有"程序已就绪，共 46 个配置文件"，没有任何按钮。功能上等于无法导出。 （推测是 FORMS 表里 wifi = 545, 422 从原版抄错了，应为 ~448+。）

P1「端口扫描」窗体下半部被裁、状态栏不可见

客户区 670×606，但结果 groupbox 在 (8,154,654,490) → 底边 644；Listbox 在 (16,172,638,458) → 底边 630； 状态栏 lbl(8,650,...) → 650 起。真机截图证实： 结果列表底边被窗口边缘切断，"程序已就绪"状态栏完全看不到。

P2「自定义IP扫描地址」布局错乱 + 面板重叠

客户区 713×547，但 groupbox(160, 470, 144, 338, "IP扫描范围 (0)") → 底边 808， 超出 261px，只露出顶部 77px 一条白板（真机截图证实）； 同时它与 groupbox(12, 470, 703, 42) 在 y 470–512 区间重叠。 其余控件（开始/停止/清空/导出、定时扫描）位置正常。

P2「IP地址计算器」底部字段被裁 ~2px

末行 entry(96, y-4=312, 150, 21) → 底边 333 > 331。 真机截图可见"可用地址数"输入框底边被切。轻微但可见。

P2except Exception 过宽

scan_ports_async 的兜底是 except Exception —— 它的本意是接住 ModuleNotFoundError， 但也会吞掉 asyncio 路径里的任何其它 bug（如回调里的逻辑错误）， 让用户以为扫完了。建议改成 except (ImportError, ModuleNotFoundError, OSError)， 其它异常往上抛。

P3网卡下拉框文字裁切出半个字形

主窗口下拉框把文字裁在 x + w - CMB_TEXT_CLIP_R，中文场景下会切出半个汉字 （截图里"以太网适配器…"被裁成"以太网遮"+残笔画）。原版按 ASCII 设计的裁剪线， 遇到 CJK 观感粗糙。可改为按字符边界裁。

P3根因提示：FORMS 尺寸表疑似抄错

上面 P1/P2 的四个布局问题，坐标在 exe 与 src 里完全一致 —— 说明它们不是改坏的，而是从原版 C# 反编译时就把 ClientSize 抄错了 （portscan 606→应约 806、ipsegment 547→应约 810、wifi 422→应约 448）。 一处修表，四处全好。建议用原版 exe 逐个量一次真实 ClientSize。

P3非 Bug：config/save 等行为差异

dialogs.f_config.save() 把值写回 cfg 但 src 版不落盘； 绿色版已补 Config.save()。此外 src 版的「一键设置IP / 自定义IP扫描地址 / IP段扫描」三个窗体是占位弹窗（"复刻版未实现"），绿色版全部真实现了 —— 这不是 bug， 是 src 落后的证据。

4.2 前端做得好的地方

  • DPI 适配是真做了：ScaledCanvas + theme.u()/ub()/lw() 全链路缩放，字体用负像素字号绕开 Tk 的点数缩放，还处理了 GDI ASCII/CJK 分档差异。
  • 弹出层架构正确：独立 Toplevel + 翻转避让 + 圆角阴影 + Esc 三道兜底， 把"菜单被状态栏吃掉"这类 Canvas 架构性无解的问题解决了。
  • 主界面像素复刻的功底扎实：theme 里每个常量都标了 [SRC]（反编译源码字面值）或 [MEAS]（截图像素实测）， 连 create_line 不画末点像素、GDI 圆角把右框临时拉宽这种坑都记了。
  • 细节还原到位：GroupBox 蚀刻框、按钮 FlatStyle 三层描边、 状态栏 7 个面板按"文字推进宽度 + 边框"反推宽度并给出验证算式。

4.3 前端待改进

  • 4 处布局溢出（§3 P1/P2）—— 根因大概率是 FORMS 尺寸表抄错，一处修复四处全好。
  • 主窗口下拉框的 ASCII 裁剪线对中文不友好（半个字形）。
  • 子窗体用绝对坐标 place()，没有任何布局管理器 → 窗体一旦 resize 就露馅。若未来要做"可调窗体"得重写。
  • 方向未定：现代化 vs 像素复刻，两套验收标准不能同时满足。

6单 exe 打包方案

方案做法体积工作量风险
A. 直接用现有根目录 IPScaner.exe 什么都不做，今天就能发9.14 MB0 发出去的是旧功能版（见 §1.1），朋友的体验比绿色版差一大截
B. 源码找回后 build.py 重打包（推荐） Phase 0 还原 src → python src/build.py → 真正的 onefile ~7-9 MB取决于 Phase 0 最干净，且 build.py 已具备归档/清理/校验
C. 直接把绿色版 onedir 重新打成 onefile 装完整 Python 3.10（含 tcl/tk）→ PyInstaller spec 里把 7 个业务模块以 .pyc 形式塞进 a.pure（PyInstaller 的 get_code_object 支持 pyc）→ --onefile ~7 MB中 需要先装 Python 3.10；pyc 直接进 PYZ 是非官方用法，要验证
D. 7z / IExpress 自解压 把绿色版 onedir 包成自解压 exe，释放到 %TEMP% 后启动 ~7 MB低 首次启动慢；易被杀软误报；不是"真"单文件
