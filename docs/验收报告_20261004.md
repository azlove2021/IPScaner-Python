## 一、⭐ 本轮最大突破：子窗体截图从"不可能"变成"已解决"

这是本轮最关键的进展，必须先讲，因为它**第三次推翻了"环境限制"这个错误结论**。

### 1.1 突破过程

| 阶段 | 结论 | 是否属实 |
|---|---|---|
| 前两轮 | "DWM/硬件合成挡 BitBlt，本机永远截不了图" | ❌ **错误** |
| 本轮初 | 修好 ctypes argtypes 后，主窗体 1372 色 ✅，子窗体仍 1 色 | 部分成立 |
| 中间 | 判定为"子窗体 Tk Toplevel 抓不到" | ❌ **错误** |
| **本轮末** | **5 个子窗体全部抓到真实像素（107~2480 色）** | ✅ **真相** |

### 1.2 真正的根因：`GetDIBits` 扫描线数传错

```python
# ✗ 我一直写错的（跨 3 个脚本）
n = gdi32.GetDIBits(mem, bmp, 0, w * h, raw, byref(bi), 0)   # 1252×729=912708 行
# ✓ 正确
n = gdi32.GetDIBits(mem, bmp, 0, h,     raw, byref(bi), 0)   # 729 行
```

传 912,708 行给 GDI 会**直接失败返回 0**，缓冲区保持全零 →
统计颜色数 = 1 → 我据此判定"这个窗口抓不出来 / 环境不支持"。

**`PrintWindow` 返回 `ret=1`（成功）但 `GetDIBits` 返回 0** —— 前者成功掩盖了后者失败，
这就是我连续两轮误判的原因。**判据必须是 `GetDIBits` 的返回值，不是 `PrintWindow` 的。**

### 1.3 附带修掉的三件事

| 问题 | 症状 | 修法 |
|---|---|---|
| `DeleteDC` 缺 argtypes | `OverflowError: int too long to convert` | `gdi32.DeleteDC.argtypes = [HDC]` |
| `update_idletasks` 不跑 `after` | 子窗体永远停在 1:1 尺寸（592×395） | 改 `root.update()` + `time.sleep(0.02)` 交替 |
| 整窗 910px 宽 stride 未对齐 | 顶层 HWND 抓取失败 | 改抓客户区 `winfo_id()` |

### 1.4 抓图方法论（已沉淀进 skill）

```python
# 唯一正确的等待姿势：update() 跑 after，sleep 让 DWM 合成
for _ in range(4):
    root.update()        # update_idletasks 不处理 after 定时器！
    time.sleep(0.02)     # tight loop 会饿死 DWM，产出全黑
```

> ⚠️ **两次"全黑"的成因完全不同**，必须分开诊断：
> - `argtypes` 缺失 / `GetDIBits` 参数错 → **像素层**失败（缓冲区全零）
> - `update_idletasks` / tight loop → **调度层**失败（窗口没被合成）

### 4.2 🔴 扫描慢的根因 —— 已定位到字节码（铁证）

**现象**：254 个 IP 扫描耗时 **17,267 ms**。

**我反汇编 `mainform.pyc` 拿到了直接证据**：

```python
# mainform.pyc:1408  _pump 开头 —— 只取一条！
msg = self.ui_q.get_nowait()          # ← 单次 get_nowait，不是循环抽干

# mainform.pyc:1455  _pump 末尾 —— 60ms 后再跑一次
self.root.after(60, self._pump)
```

**数学验证**：
```
254 个 IP × 1 条消息/次 × 60ms/次 = 15,240 ms  理论下限
实测 17,267 ms（多出的 2s 来自网络超时与首帧开销）
→ 吻合度 88%，根因确认
```

**修法**（把单次改成抽干）：
```python
def _pump(self):
    try:
        for _ in range(200):          # 单轮最多抽 200 条，防止饿死事件循环
            try:
                msg = self.ui_q.get_nowait()
            except queue.Empty:
                break
            ...原处理逻辑...
    finally:
        self.root.after(60, self._pump)
```
**预期：17.3s → 约 2~3s**（受网络 ping 超时限制，UI 刷新不再是瓶颈）。

⚠️ 这需要**改 `src/` 源码后重新打包**，或用运行时钩子 monkey-patch `_pump`。

## 八、本轮方法论教训（最重要）

> **前两轮把"抓不到图"当成环境限制写进了文档和 Obsidian 知识库，
> 等于把一个代码 bug 包装成了不可抗力。**

三个教训：

1. **"工具失败"≠"环境不允许"**。同一个 bug 家族（ctypes/GDI 参数错误）已经骗了我 3 次：
   句柄截断 → BGR 通道 → `GetDIBits` 扫描线数。每次的表现都是"抓出来是黑的"。

2. **判据要看真正失败的那一步**。`PrintWindow` 返回成功掩盖了 `GetDIBits` 返回 0，
   我如果同时打印两个返回值，10 分钟就能定位。

3. **断言全绿 ≠ 界面能看**。subagent 的几何检测（z 序 + 坐标）只能*怀疑*，
   必须**真的把图抓出来用眼睛看**才算验收。

## 十一、v1.25.5 / v1.25.6：悬浮高亮两处缺陷（2026-10-08 第八段）

用户反馈：「为什么有些 button，悬浮的时候还是会显示浅蓝色的方块呀。」（附截图：工具条上一个
浅蓝矩形盖住「开始」）。这直接推翻了 v1.25.4 里「显示正常」的结论，于是回到字节码层重新定位。

### 11.1 缺陷 9 —— 工具条按钮：不透明方块盖住按钮自己的文字

**根因**（`mainform.pyc`，两处叠加）：
1. `_hover_rect(box)` 用 `create_rectangle(*box, fill=T.C_MENU_SELECT, outline='', tags='fx')`
   画高亮，`box` 来自 `self.regions`，而 regions 存的是**设计 1:1 坐标**
   （`on_motion` 里 `_hit(e.x/S, e.y/S)` 印证）→ 方块先落在错位处，最多要等 500ms 的
   sweep 才被搬正；
2. 它不透明，而且是 `refresh_fx()` 里**最后**画的 → 层序最上 → 正好盖住按钮自己的
   label text → 用户看到「没有字的浅蓝方块」。

**像素实证**：用户截图里 `#C9E4FF` 占 2656px、块内**零个文字像素**；
测试架复现 `id=1082 rectangle bbox=(265,62,350,96) fill=#C9E4FF`，层序在
`id=42 text '开始'` 之上。

**修法**：包一层 `MainForm._hover_rect` —— 建完立刻按 S 归位，并改成**描边环**
（外扩 3S、`fill=''`、`outline=#0072EF`、宽 2S），再把同区域文字 `tag_raise` 到最上层；
sweep 里加 `sweep_hover_rings` 兜底。`IPSCANER_NO_HOVER_RING=1` 可关。

### 11.2 缺陷 10 —— 顶级菜单项：高亮块画在设计坐标，只有菜单项的 2/3 大

**关键发现：菜单项根本不走 `_hover_rect`。** 源码模式 dump 画布图元（悬浮「快捷工具」）：

```
id=1171 polygon bbox=(1, -1, 102, 25)  fill=#E9F1FD  tags=['fx']            ← 设计坐标
id=1173 text    bbox=(38, 5, 134, 29)  fill=#1A1A1A  tags=['fx','current']   ← 缩放坐标
```

块与文字分属两套坐标系：块只有 96px 宽（应 146px）且偏左上。与缺陷 9 的差别是
—— 菜单文字被重画成 fx text 叠在块上层，**字没被盖住**；坏法是尺寸/位置不对。

**修法**：包一层 `MainForm.refresh_fx`，悬浮对象是 `menubar` 时按 S 就地缩放该块，
幂等标记 `ipscaner_menufix`（每次 refresh_fx 都重建，必须每轮处理 + 靠标记防二次缩放）。
底色认整族：`MENUBAR_HOVER #E9F1FD` + `MENUBAR_ACTIVE #DCE8FA`
（只认前者会在运行中切到激活态时**静默失效**，真机复现：B 态 ROI 主色 (220,232,250)×1237）。
顺带发现 `src310/` 只是早期手工还原的对照源码，**真正在跑的是 `build_green/*.pyc`** ——
两边的 `theme.py` 常量并不一致，判断问题必须以 .pyc/真机为准。

### 11.4 方法学（三条，已写进 gui-screenshot-audit skill）

1. **鼠标事件送不到窗口 → A/B 逐像素相等 = 假阴性**。本机屏幕被一个覆盖
   (14,134)-(3437,1975) 的浏览器窗口压着，必须先 `SetWindowPos(HWND_TOPMOST)`；
   而 `HWND_TOPMOST(-1)` 不声明 argtypes 会被截成 `0x00000000FFFFFFFF`，
   `SetWindowPos` 静默返回 0。且要用 `WindowFromPoint` 反查 class 证伪。
2. **判据必须是 A/B 差分**，不能只数悬浮态颜色：网格浅蓝、菜单栏渐变、控件描边都会混进来
   （基线就有 1854 个假阳性）。容差收到 ±4（菜单高亮的 1px 描边 `#CFE3F7` 与
   缺陷色 `#C9E4FF` 只差 6/1/8，±8 下每次假报 300+ 个方块像素）。
3. **按标题选窗要加"面积最大"兜底**：鼠标停在网格上会弹出产品自带的悬浮提示
   （独立 TkTopLevel，标题与主窗相同，260x53），否则会抓到它而以为界面全变了。
